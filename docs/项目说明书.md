# 医疗多智能体项目说明书

> 维护日期：2026-09-17  
> 适用范围：当前开发与联调环境

## 1. 项目概述

本项目是一个面向医疗咨询场景的多智能体服务，目标是在统一的聊天接口后提供：

- 症状采集、急症识别、候选疾病分析与就诊建议；
- 文档知识库、医学知识图谱和运营数据的联合问答；
- 会话级短期记忆与跨会话长期记忆；
- PostgreSQL、Redis、Milvus、Neo4j 等基础设施的本地 Docker 化运行。

当前已实现的核心 Agent 包括：

1. **智慧问诊 Agent**：围绕症状采集、追问、候选疾病和结论生成执行多轮流程。
2. **知识问答 Agent**：基于文档 RAG、知识图谱、运营数据查询和多通道融合回答知识问题。
3. **Supervisor**：统一承接用户消息，管理会话状态、长期记忆，并将任务分派给问诊或知识问答能力。

> 本项目输出的是辅助性问诊与知识检索结果，不应视为确诊、处方或急救替代方案。涉及急症或用药决策时，应由执业医师进一步评估。

## 5. 核心业务流程

### 5.1 智慧问诊流程

问诊图按以下顺序执行：

1. **加载患者上下文**：根据 `patient_id` 从 PostgreSQL 读取年龄、性别、过敏史、既往病史和近期问诊记录。
2. **急症识别**：对胸痛、呼吸困难、意识障碍等高风险信息优先处理；命中急症时直接建议急诊。
3. **症状标准化**：专用的非 Thinking LLM 提取症状，再通过 Neo4j 精确匹配与 Milvus 语义匹配归一化。
4. **候选疾病检索**：从 Neo4j 查找疾病—症状关系，按已确认症状覆盖率排序；多症状命中候选优先于单症状命中候选。
5. **症状追问**：根据候选疾病之间的差异性症状生成下一轮问题。
6. **结论审查**：LLM 审查图谱首位候选是否合理。候选明显不合理时，生成一个具体的待排病症，而不直接沿用不合理图谱候选。
7. **保存记录**：问诊结束后将结果写入 `consultations`。

问诊结论不会向用户展示数值置信度。LLM 生成的替代病症会以“待排”形式展示，而不是确诊结论。

### 5.2 知识问答流程

Knowledge Agent 可使用以下工具：

| 工具 | 数据来源 | 适用场景 |
| --- | --- | --- |
| `search_knowledge_docs` | Milvus `knowledge_docs` 集合 | 指南、说明书、SOP、医学文献等文档内容 |
| `search_knowledge_graph` | Neo4j | 疾病、症状、药物、检查、科室之间的关系 |
| `search_knowledge_sql` | PostgreSQL | 问诊量、库存、统计、排名等运营数据 |
| `search_knowledge_multi` | 文档、图谱与可选 SQL | 需要多个来源综合回答的复杂问题 |

文档 RAG 的基本步骤为：查询改写、查询向量生成、Milvus 召回、重排序、LLM 基于文档上下文生成带来源的回答。

NL2SQL 工具优先复用显式注入的数据库会话；默认聊天调用链未注入会话时，工具按次创建并在调用结束后关闭会话，不将会话保存在全局 Knowledge Agent 中。


## 6. 环境准备与启动

### 6.1 前置条件

- Docker Desktop 或兼容 Docker Compose 的运行环境；
- Conda；
- Python 3.13；
- 可用的 DeepSeek API Key 与 DashScope API Key；
- 可访问 DeepSeek 与 DashScope 的网络。DashScope Embedding 使用 HTTPS 服务，代理或网络不稳定时可能出现 TLS EOF 错误。

### 6.2 创建并安装 Conda 环境

项目当前使用的环境名为 `multi-agent`：

```powershell
conda activate multi-agent
python -m pip install -r requirements.txt
```

如需新建环境：

```powershell
conda create -n multi-agent python=3.13
conda activate multi-agent
python -m pip install -r requirements.txt
```

### 6.3 配置环境变量

复制模板：

```powershell
Copy-Item .env.example .env
```

重点配置项：

| 配置项 | 用途 |
| --- | --- |
| `DEEPSEEK_API_KEY` | 问诊、Supervisor、Knowledge Agent 的聊天模型调用 |
| `CHAT_MODEL` | 聊天模型名称 |
| `DASHSCOPE_API_KEY` | 文档、症状、长期记忆等文本向量化 |
| `EMBEDDING_MODEL` | Embedding 模型名称 |
| `DB_*` | PostgreSQL 连接信息 |
| `REDIS_*` | Redis 连接信息 |
| `MILVUS_HOST`、`MILVUS_PORT` | Milvus 连接信息 |
| `NEO4J_*` | Neo4j 连接信息 |
| `MINERU_API_URL` | 可选 MinerU 文档解析服务地址；未配置时文档导入自动回退到 LlamaIndex |

不要提交真实的 `.env`、API Key 或生产环境密码。

### 6.4 启动基础设施

```powershell
docker compose up -d
docker compose ps
```

启动后建议确认 PostgreSQL、Redis、Milvus、MinIO、Neo4j 均处于运行状态。

Neo4j Browser：

```text
http://127.0.0.1:7474
```

Milvus Attu：

```text
http://127.0.0.1:3000
```

### 6.5 启动 API 服务

```powershell
conda activate multi-agent
python -m uvicorn src.main:app --port 8080 --reload
```

基础健康检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8080/health
Invoke-RestMethod http://127.0.0.1:8080/health/deps | ConvertTo-Json -Depth 5
```

`/health/deps` 会检查 PostgreSQL、Redis、MinIO、Milvus 与 Neo4j 的可用性。若任一依赖不可用，接口状态会显示为 `degraded`。

## 7. 数据初始化

### 7.1 初始化顺序

首次启动开发环境时，建议按以下顺序执行：

```powershell
conda activate multi-agent

alembic upgrade head
python scripts/init_postgres.py
python scripts/init_neo4j.py
python scripts/init_symptom_index.py
```

| 命令 | 作用 |
| --- | --- |
| `alembic upgrade head` | 创建或升级 PostgreSQL 表结构 |
| `python scripts/init_postgres.py` | 从 `data/raw/medical.json` 导入科室、症状、药品、疾病与关联数据；同时创建开发联调患者 `patient_id=42` |
| `python scripts/init_neo4j.py` | 从 `data/raw/medical.json` 构建 Neo4j 医学知识图谱 |
| `python scripts/init_symptom_index.py` | 从 Neo4j 的症状节点创建 Milvus `symptom_index` 向量索引 |

> **注意：** `init_neo4j.py` 会先删除当前 Neo4j 图数据，再重新导入。已有手工维护的图谱数据时，不要直接运行该脚本。

### 7.2 开发联调患者

`init_postgres.py` 会创建或更新固定测试患者：

```text
patient_id: 42
```

可用于本地聊天接口联调。生产接口中必须根据认证与授权关系校验 `patient_id` 的归属，不能信任客户端任意传入的患者 ID。

## 8. 知识文档向量库导入

### 8.1 放置文件

将 PDF、Word、Markdown 或文本文件放入：

```text
scripts/data/
```

例如：

```text
scripts/data/高血压指南.pdf
```

### 8.2 导入命令

```powershell
conda activate multi-agent
python scripts/import_knowledge_doc.py --file 高血压指南.pdf --doc-type guideline --category 心血管
```

支持的文档类型：

| `--doc-type` | 含义 |
| --- | --- |
| `guideline` | 临床指南 |
| `drug_instruction` | 药品说明书 |
| `sop` | 医院制度或 SOP |
| `literature` | 医学文献 |

相同文件名再次导入时，系统会使用文件名计算文档 ID，并替换该文件名对应的旧分块，适用于文档更新。

### 8.3 使用本地解析回退

未配置 `MINERU_API_URL` 时，导入流程自动使用 LlamaIndex 解析文档。也可在当前 PowerShell 会话中强制关闭 MinerU：

```powershell
$env:MINERU_API_URL = ""
```

文档解析可以本地执行，但文本向量化仍会调用 DashScope Embedding；导入和检索均要求 DashScope 网络可用。


## 9. API 使用说明

### 9.1 非流式聊天接口

接口：

```text
POST /api/v1/chat
```

请求体：

```json
{
  "user_id": "test-user-001",
  "session_id": "inquiry-001",
  "message": "我头痛发热两天了，体温38.5度，应该挂哪个科？",
  "patient_id": 42
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` | string | 当前登录账户或调用方标识 |
| `session_id` | string | 会话标识；同一问诊多轮必须保持一致 |
| `message` | string | 用户本轮消息 |
| `patient_id` | integer / null | PostgreSQL `patients.id`；用于加载病史和保存问诊记录 |

PowerShell 调用示例：

```powershell
$body = @{
    user_id    = "test-user-001"
    session_id = "inquiry-001"
    message    = "我头痛发热两天了，体温38.5度，应该挂哪个科？"
    patient_id = 42
} | ConvertTo-Json

Invoke-RestMethod   -Method Post   -Uri "http://127.0.0.1:8080/api/v1/chat"   -ContentType "application/json"   -Body $body
```

响应：

```json
{
  "reply": "...",
  "session_id": "inquiry-001"
}
```

### 9.2 SSE 流式聊天接口

接口：

```text
POST /api/v1/chat/stream
```

请求体与非流式接口相同。活跃问诊会在模型生成澄清、追问或结论正文时，逐块发送内容，而不是等待整段回复后再拆分。症状抽取、术语转换和候选审查等内部内容不会推送给客户端。

`done` 在本轮问诊状态保存或清理完成后发送；执行失败时发送 `error`，不发送 `done`，也不保存未完成的问诊状态。响应采用 Server-Sent Events，事件数据包含：

```text
data: {"type":"token","content":"..."}

data: {"type":"done","session_id":"..."}

data: {"type":"error","message":"..."}
```

### 9.3 会话与患者 ID 规则

- 同一用户的同一次问诊必须使用相同 `user_id` 与 `session_id`；
- 新问诊应使用新 `session_id`，避免复用已经异常中断的历史 checkpoint；
- `patient_id` 必须存在于 `patients` 表，否则保存问诊记录时会触发外键错误；
- 开发环境可使用 `init_postgres.py` 创建的 `patient_id=42`。

### 10.4 真实联调建议

建议使用新的 `session_id`，依次验证：

1. 问诊首轮：症状抽取、候选疾病、追问或结论；
2. 问诊续轮：使用相同会话继续回答追问；
3. 急症：胸痛、呼吸困难等信息是否进入急诊提醒；
4. 文档知识问答：导入文档后，回答是否包含文档来源；
5. 图谱问答：疾病、症状、检查或科室关系能否正确召回；
6. 长期记忆：跨会话是否能通过保存与检索工具读取重要信息。

## 11. 常见问题与排障

### 11.1 Neo4j 容器持续重启

如果日志包含主机名无法解析的异常，例如 `UnknownHostException`，检查 `docker-compose.yml` 中 Neo4j 服务是否包含固定 `hostname` 与主机名映射。当前配置已使用固定 Neo4j 主机名，以避免 JVM 初始化日志组件时解析失败。

### 11.2 DashScope Embedding TLS EOF

若出现如下错误：

```text
SSLError: UNEXPECTED_EOF_WHILE_READING
```

通常发生在 DashScope Embedding HTTPS 请求阶段。检查：

1. 本机网络是否正常；
2. 本地代理是否稳定；
3. DashScope API Key 与 Embedding 模型配置是否正确；
4. 网络恢复后重试文档导入或检索。

本地文档解析成功不代表查询向量生成成功；文档 RAG 的查询阶段仍依赖 Embedding 服务。

### 11.3 Thinking 模式与结构化输出冲突

症状结构化提取使用 Function Calling。Thinking 模式不支持当前结构化输出实现所需的强制工具选择，因此项目为症状提取单独创建关闭 Thinking 的模型实例。不要将该专用模型替换回主问诊模型。

### 11.4 图谱候选明显不合理

候选疾病基于症状关系图谱，不能将症状覆盖率等同于临床确诊概率。当前流程已：

- 使用已确认症状覆盖率替代疾病自身症状覆盖率；
- 优先多症状命中候选；
- 禁止单症状候选直接收敛为诊断；
- 在结论前由 LLM 审查图谱候选；
- 对明显不合理候选生成具体的待排病症，而非直接沿用图谱首位候选。

## 12. 当前边界与后续建议

- 当前 Agent 仅覆盖问诊与知识问答 Worker；不存在的报告、药物或运营 Worker 不应在调用链中声明或引用。
- 文档向量化和查询依赖外部 Embedding 服务；如需完全离线部署，应替换为本地 Embedding 模型并重新构建向量库。
- `patient_id` 的授权关系尚需在 API 层与认证系统联动；开发环境不能作为生产授权实现。
- 图谱数据来自 `medical.json`，缺少疾病流行度、典型症状权重、季节性和循证等级等临床先验；结果应作为辅助信息使用。
- 生产部署应补充认证、审计、速率限制、监控、脱敏与权限控制。
